**Title:** refactor: plan 021 — workflow modules

## Summary

`Extend/` is replaced with a module registry. Each plugin's module lists its triggers, conditions, actions and data items. Free vs Pro is now the folder: Pro modules live in `includes/Pro/`, which the free zip leaves out. This is a refactor only. Behavior is unchanged, and stored step ids (`data.block`) stay the same.

Builds on Khoa's PR #21 (module registry). The commits that reuse its code carry `Co-authored-by: Khoa Ta`. PR #21 was branched before M1, so it isn't merged or rebased here; its parts are reused and adapted, as listed below.

### Layout (`includes/Workflow/`)
```
ModuleRegistry.php
Modules/      Module, YayMatikModule, WoocommerceModule
Triggers/     OrderTrigger, OrderCreated, OrderStatusChanged
Conditions/   Criteria
Actions/      SendEmail, SendInternalEmail, ChangeOrderStatus, AddOrderNote, UpdateOrderMeta, GenerateCoupon
DataItems/    OrderData, CustomerData, OrderItemData, SiteData
Core/         Steps/ (contract)  Data/  Definition/  Runtime/  Storage/  Email/  Coupon/
includes/Pro/Workflow/Modules/   YayMatikProModule, WoocommerceProModule
```
Namespaces follow the folders (`YayMatik\Workflow\Core\Runtime\…`, `YayMatik\Pro\Workflow\…`), and `tests/Unit` follows `includes/` the same way. The moves are their own commits (`git mv` only), so file history is kept.

### Modules
- `abstract class Module` has `id()`, `label()`, `description()`, `logo()`, `active()`, and `triggers()` / `conditions()` / `actions()` / `data_items()` (class names).
- `ModuleRegistry` uses the Pro modules when their classes exist, otherwise the free ones. Then it runs the `yaymatik_modules` filter (class names). Anything that isn't a `Module` subclass is ignored, and a taken id (module, step or data item) keeps its first owner. Steps are built once.
- The catalog sends each step's module id as `plugin`. Steps no longer declare `plugin()` or `module()`, and the catalog drops the `module` key.
- The Pro modules extend the free ones and have empty bodies for now. The `Pro/Workflow/{Triggers,Actions,Conditions}/` folders appear with the first Pro step.

### Admin app
- Catalog triggers and actions without a TS folder register themselves, with their form and checks drawn from their PHP fields.
- `StepId` / `WorkflowPlugin` are widened, and the picker skips steps whose plugin isn't in the catalog.
- `PluginIcon` draws the logo URL with a CSS mask in the tile's text colour, so it keeps the tones and works in dark mode. An unknown plugin gets a neutral tile. There's no `dangerouslySetInnerHTML`.

### Release
- `./run.sh release` builds `release/yaymatik.zip` without `includes/Pro/` (`.distignore`). `./run.sh release pro` builds `release/yaymatik-pro.zip` with it.
- Checked: the free classmap has 0 Pro classes, and `assets/logos/` ships in both zips. The free zip was installed on a local site: admin page, editor, picker logos and a template install all work.

## Beyond the leader's layout
- **`Triggers/` folder:** triggers are what modules register, like conditions and actions, so they sit beside them.
- **`data_items()` in modules:** a plugin owns its data types as well as its steps, so the module lists both. `OrderItemData::standalone()` is false, which keeps order_item reachable only through `order.items`, as before.
- **`Core/` for the engine:** the top level shows what modules register, and everything a module uses but doesn't register sits under `Core/`.
- **`Core/Steps/` = contract only:** the base classes, `Field`, `StepResult`, `StepIcons` and `StepRegistry`. The steps themselves live in their kind's folder.
- **`DataItems/` at the top level:** data items are registered by modules, the same as steps. `Core/Data/` keeps `DataItem`, `Scope`, `Template` and the rest.
- **Folder = plural of its base class:** you can tell where a new class goes from what it extends.
- **Steps drop `plugin()`:** the registry already knows which module listed a step, so a step can't name the wrong plugin.
- **Logos as SVG files (`logo()` = URL):** a Yay plugin can define its module in its own repo. There's no markup to sanitize, and `LOGO_TAGS` / `clean()` are gone.
- **TS registers catalog steps without a TS folder (from PR #21):** another plugin's trigger or action works in the editor with no admin-app change.
- **Trigger listeners register on `init`:** before, the registry was first read on `plugins_loaded`, so a plugin loaded after YayMatik would have been left out silently. A plugin adds the filter before `init`, and `./run.sh check-late-module` checks this. It fails with the old timing.
- **`./run.sh release pro`:** it builds the Pro zip from the same tree, so Pro needs no second repo or build script yet.
