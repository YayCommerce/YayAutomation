**Title:** feat: plan 026 — M7 PR B: Settings page, health check panel, sticky header

## Summary

The UI of M7 (ROADMAP-dev M7.6, M7.7) on top of PR A (#30). Settings is now one page with three cards: Cart tracking, Emails and Run history. They read and save `GET` / `PUT /settings`. A fourth card, Health check, lists the problems `GET /health/checks` finds, and each fixable one has a button that calls `POST /health/fix`. Save changes sits in the app header. Leaving with unsaved changes asks first.

The app header now stays pinned under the WordPress admin bar on every page. The workflow overview scrolls as a whole page with its title bar pinned under the header.

The only PHP change is one body class (`yaymatik-page`) in `AdminPage::admin_body_class`. There is no new REST route, no new PHP class and no DB change.

About 32 files, +1.9k, one commit per checkpoint.

## Commits
- **B1 Settings page** (d55b0f0)
  - The form uses @tanstack/react-form with a valibot schema whose ranges match PHP's (Vitest). Server `errors[].field` shows on that field. Nothing is saved when a value is out of range.
  - Save changes goes into the app header through a portal into `#yay-header-actions`. It is shown only on Settings and only once the settings load. It is never disabled: a spinner shows while saving, and a click during a save returns that save (no second PUT). Saving with nothing changed is still a real save.
  - Abandon minutes and capture guest emails are hidden while tracking is off. Turning tracking off resets both to their saved values and clears their errors.
  - Leaving with unsaved changes: in the app, an "Unsaved changes" dialog offers Discard changes or Save changes. Close or Esc stays on the page. Tab close, reload and other wp-admin pages get the browser's `beforeunload` prompt, only while there are unsaved changes.
  - The cards are built from YayUiKits parts only: `Card`, `Field orientation="responsive"`, `InputGroup` with unit addons, and `Alert`.
- **B2 Health check panel** (667b6af)
  - It is the last card of Settings and is not part of the form, so it has no effect on unsaved changes, Save or the leave dialog.
  - There is one scan per visit, none on focus or reconnect, and no polling (a scan reads up to 500 runs). Later scans run only on "Check again".
  - One mutation per fixable check, so only that row's button spins. On success the panel takes the `checks` from the response and cancels any scan still in flight, since it may predate the fix.
  - Problems come first, then `jobs_late` (info, with a link to the cron guide); ok checks are hidden. Counts use `_n`, and a capped count reads "N+". The summary is "N problems · checked {time}", "No problems · checked {time}" or "Checked {time}".
  - `routes/settings/api/request.ts` parses errors for both the settings and health clients; `workflow.api.ts` is unchanged.
- **Sticky app header** (489e7f9)
  - The header is `position: sticky` (no JS), at `top: var(--wp-admin--admin-bar--height, 32px)` above 600px and `top: 0` at 600px and below, where the admin bar scrolls away. It has z-40, so every overlay (z-50 and up) and the admin menu flyouts stay above it, and it has a bottom border. A shadow shows once the page has scrolled.
  - The logo works like YayCurrency's: a 50×50 `assets/images/yaymatik-logo.png` on a `#FFF5DB` tile flush with the left edge of the header (a faint tint in dark).
  - The editor's full height uses the admin bar variable, so there is no extra scroll at 782px and below. The workflow overview now scrolls as a page, with its title bar sticky under the header (z-30).
  - On the YayMatik page only (body class `yaymatik-page`), `#wpbody-content` has no bottom padding and `#wpfooter` is hidden, so full-height pages get one scrollbar.
- **Header colours from theme tokens** (0ee2894): the logo tile (`--yay-logo-tile`, `bg-logo-tile`) and the scroll shadow (`--yay-header-shadow`, `shadow-header-shadow`) come from `styles/theme.css`, with light and dark values that look the same as before. They no longer use `dark:`.

  - ROADMAP-dev M7: M7.1–M7.5 and M7.8 are marked ✅ (PR #30), the status line says PR B is open, M7.6 and M7.7 are marked ⏳, and M7 Follow-ups are added.

**B2 Health check** (SQL in Sequel Ace on copies, so no real run changes)

Setup: pick a completed run S as the source and make three completed copies of it. A re-queued copy has an empty queue, so it runs no step and sends no email or coupon.
```sql
SELECT MAX(id) INTO @max FROM wp_yaymatik_runs;
INSERT INTO wp_yaymatik_runs (workflow_id, version_id, trigger_id, subject, status, position, scope, parent_run_id, root_run_id, depth, started_at, finished_at)
SELECT workflow_id, version_id, trigger_id, subject, 'completed', '{"queue":[]}', scope, 0, 0, 0, UTC_TIMESTAMP(), UTC_TIMESTAMP()
FROM wp_yaymatik_runs, (SELECT 1 n UNION SELECT 2 UNION SELECT 3) t WHERE id = S;
UPDATE wp_yaymatik_runs SET root_run_id = id WHERE id > @max;
SELECT id FROM wp_yaymatik_runs ORDER BY id DESC LIMIT 3;  -- X, Y, Z
```
1. All ok: "No problems found" and "Checked {time}".
2. Queued run: run `UPDATE wp_yaymatik_runs SET status='queued', finished_at=NULL, started_at=UTC_TIMESTAMP() - INTERVAL 10 MINUTE WHERE id=X;`. Click Check again and a queued-runs problem shows. Its fix button gives the "1 run queued again." toast and the row goes away.
3. Running run: run `UPDATE wp_yaymatik_runs SET status='running', finished_at=NULL WHERE id=Y;`. Click Check again, then use the recover fix: the "queued for recovery" toast shows.
4. Waiting run: run `UPDATE wp_yaymatik_runs SET status='waiting', finished_at=NULL, wait_until=UTC_TIMESTAMP() - INTERVAL 20 MINUTE WHERE id=Z;`. It shows under queued runs. With `INTERVAL 10 MINUTE` it doesn't.
5. In Scheduled Actions, cancel the pending `yaymatik_cleanup`. Click Check again, then the fix: "The daily cleanup is scheduled again."
6. Late jobs show as info with a link to the cron guide (new tab) and no button.
7. Loading shows skeleton rows. Block `/health/checks` in DevTools: "Couldn’t run the health check." shows with Try again.
8. At 375 the fix button sits under the text.
9. Clean up: let the queued and recovery jobs run (or Run them in Scheduled Actions), then run `DELETE FROM wp_yaymatik_run_steps WHERE run_id IN (X, Y, Z); DELETE FROM wp_yaymatik_runs WHERE id IN (X, Y, Z);`.

## Known limits and follow-ups
These are also in ROADMAP-dev M7 → Follow-ups.
- **Editor canvas:** the mouse wheel zooms and panning needs a drag (ReactFlow defaults since F1), so you can't scroll to a step added below the view. Proposal: wheel and trackpad pan, Ctrl/Cmd + wheel zooms, and a new step is brought into view.
- **Leave dialog titles differ:** Settings says "Unsaved changes" and the editor says "Leave without saving?".
- **Unused dependencies** in `apps/admin-page`: zod, react-hook-form, @hookform/resolvers and @formisch/react.
- **Duplicated code:** `routes/settings/api/request.ts` repeats the private `request()` of `workflow.api.ts`.
- **Other tabs:** settings changed in another tab show only after a reload (no refetch).
- **Health check reach:** it can only be reached once the settings load.
- The health check limits from PR A still apply (500-run read, 50 fixes per call).
