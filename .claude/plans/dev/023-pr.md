**Title:** feat: plan 023 — M2 PR A: Wait + run history backend

## Summary

The M2 backend (ROADMAP-dev M2.1–M2.5): a Wait step, cancelling waiting runs when a workflow is turned off or updated, runs stopping right away once their workflow is off, runs REST with filter / paging / total, workflow run stats, and product grid email blocks with the cross-sell / upsell data fields. The 4 cross-sell / upsell templates can now be installed. `pending.ts` and the "coming soon" code it served are gone: PHP now has every step and data field the admin uses.

70 files, +1867 −615, one commit per checkpoint (CP1–CP5). The UI (Wait form polish, runs table, run detail, dialogs, list columns) is PR B.

## What changes
- **Wait** (`Actions/Wait`, YayMatik module, picker section Flow, clock icon): `delay` = whole number + unit (minutes, hours, days, weeks), default 1 day, up to a year per unit. Fixed seconds (a day is 86400). The run waits and its Action Scheduler job resumes it. `number_unit` now falls back to its default unit (it took the first unit). TS keeps its custom form, moved to the PHP shape.
- **Cancel** (`Runtime/Cancellation::waiting()`): REST Deactivate, REST Apply and the rate-limit pause cancel the workflow's waiting runs. Their waiting step rows become `cancelled` (new `run_steps` status), with the same reason. Deactivate and Apply responses add `cancelledRuns`. Action Scheduler jobs are not unscheduled: a cancelled run's job finds nothing to take and does nothing. Apply leaves queued and running runs on their pinned version.
- **Stop right away:** before each step, and after saving a wait, the Executor reads the workflow's status fresh (a direct query, not the object cache). Once it is off, the run ends `cancelled` ("The workflow was turned off."). When a run ends this way or before its first step, its open step rows (`running`, `waiting`) are closed, which fixes a recovered first step left `running`.
- **Runs REST:** `GET /workflows/{id}/runs?status=a,b&page=n` → `{ items, total }`. An item adds `subjectLabel` ("Order #1012", the real order number), `subjectUrl` (null once the order is gone) and `stepsRun`; an unknown status is a 400. `GET /runs/{id}`: each step adds `stepType` from the pinned version's graph.
- **Workflow stats:** `runs30d`, `lastRunAt`, `waitingRuns` (all statuses count), from one grouped query for the list.
- **Data fields:** `order.cross_sell_products` / `order.upsell_products` (email blocks, not conditional), `order.has_cross_sells` / `order.has_upsells`, `customer.paid_order_count` (processing + completed, by account and billing email). `Email\ProductGrid`: suggestions from the order's lines (a variation reads its parent), merged, minus products in the order, published + visible + in stock, at most 4. HTML is an email-safe table, 2 per row (image, name, price, link). Text is one line each, "Name — price — URL". No product → '', so the block is left out. The catalog sends `block: true` for these fields. Preview with sample data shows the store's 4 newest products.
- **TS:** `pending.ts`, `isComingSoon`, `canInsert`, the coming-soon flags on steps and variables, `comingSoonStep` and `allowPending` are deleted. `ComingSoonChip` stays (the AI describe box). Meta types: data item `icon`, field `valueType` and item `relations` are required. New REST types: `RunListItem`, `WorkflowRunsPage`, the `stepType` on run steps, the workflow stats and `cancelledRuns`.

## Decisions
- **D1:** Wait is an action in the YayMatik module, with `Field::number_unit('delay')` and per-unit max in `validate()`.
- **D2:** PR A does the TS minimum: the PHP shape, the 4 templates, no stub, fixture refreshed. The generic form can't draw `number_unit`, so the Wait form stays, on the new shape.
- **D3:** `run_steps.iteration` / `attempt` stay as design §2 lists them; M2 doesn't write them.
- **D4:** One cancel path, `Cancellation`, under the workflow lock for REST. It selects the waiting ids, then cancels those still waiting in one UPDATE. No Action Scheduler unschedule.
- **D5:** Fresh status check before each step (and after a wait); open step rows close when a run ends early.
- **D6:** Per-workflow runs list and run detail only; no global list, no cancel / retry endpoints.
- **D7:** Run stats on workflow responses, one grouped query for the list.
- **D8:** Product grid as data fields marked `block`; samples from the store's newest products.
- **D9:** `pending.ts` and its coming-soon branches deleted.
- **D10:** No new Validator issues.

## Behavior changes
- Turning a workflow off now stops a run that's already going, before its next step (before, only runs not started yet were cancelled).
- Apply (Update) cancels waiting runs.
- `GET /workflows/{id}/runs` returns `{ items, total }` (was `{ items, hasMore }`).
- The 4 cross-sell / upsell templates are no longer "Coming soon".

## Testing
- PHPUnit 451, Vitest 209, phpcs and ESLint clean (the 3 ESLint warnings are in the YayUiKits copies in `components/ui`).
- `./run.sh check-runs` on the local site, all pass. New checks: a 1-minute Wait's own Action Scheduler job resumes the run; Deactivate and Apply cancel the waiting run (`cancelledRuns` 1, reason, step row `cancelled`) and its leftover job does nothing; the rate-limit pause cancels it; turned off mid-run, the next step never runs; runs REST filter / total / subject / steps run / step types and workflow stats.
- Product grid on a real order with cross-sells and on the email preview (sample data): the block replaces its paragraph, styles inlined; an empty block leaves no `<p></p>`.

## Unused code noticed (not changed)
- TS action `provides`: `providedByAction()` in `steps/core/variables.ts` and the action branch of `availableData()` in `model/validation.ts`. PHP sends `provides` for triggers only, so they always read `[]`.

## Before you pull (other dev sites)
- **Run `composer dump-autoload` after pulling.** The autoloader uses a classmap, so new PHP classes (`Actions/Wait`, `Runtime/Cancellation`, …) aren't found until it is rebuilt: Wait is missing from the catalog, and runs fail on the missing class.

## Review fixes (CP2, /code-review high)
- A Deactivate that lands while a Wait step runs no longer leaves the run waiting: the Executor checks the status again after saving the wait.
- `WorkflowRepository::is_active()` throws when the status query fails, so a DB error never reads as "turned off".
- `is_active()` now sits above `live_version_id()`'s docblock, which had been split from its function.
- `RunStepStore::cancel_waiting()` touches only the runs this call cancelled (by id), not every past cancelled run.
- `Worker::start()` reads the fresh status (`is_active()`), as the Executor does; `find()` only tells deleted from off.
- Design §3 describes the cancel as it is: select the waiting ids, one UPDATE for the runs, then their step rows.
- Both cancel reasons live in `Cancellation` (`turned_off()`, `updated()`).
- The open step statuses are one list, `RunStepStore::OPEN`, used by the SQL and the test fake.

## Review fixes (CP3, /code-review high)
- An unknown `status` in `GET /workflows/{id}/runs` is a 400, not every run.
- `stepType` is `null` (not `''`) for a node with no step type.
- `RunPresenter::item()` reads the subject itself, through a private `subject()`; the test-only order lookup param is gone (tests use the `wc_get_order` stub).
- Docblock and blank-line nits.

## Notes
- Run stats (`runs30d`, `lastRunAt`, `waitingRuns`) come with every workflow response, not only list + GET, so a save's response can replace the cached workflow without dropping them.
