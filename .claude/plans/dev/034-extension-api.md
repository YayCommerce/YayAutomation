## Goal

A plugin adds triggers, actions, data fields, data items, templates and an iframe editor to YayMatik through `yaymatik_register` and a declarative registrar. A broken extension never breaks core, and a deactivated one never breaks a workflow.

## Approach

### Shape

- **Public layer** `includes/Api/` (namespace `YayMatik\Api`): `Api` (VERSION, `references()`), `Registrar`, `Module`, interfaces `Run`, `CustomerView`, `CartView`, and the hook `yaymatik_fire`. Declarations are arrays (fields, type names); callbacks are any PHP callable. No public class wraps an internal one: there are no `Field`, `Type`, `Ref`, `Result`, `Values`, `RunContext`, `EmailContext` (D16).
- **Adapters** `includes/Workflow/Extension/`: `ExtensionModule extends Module`, `ExtensionTrigger extends Trigger` (no `listen`: the event arrives through `Fire`), `ExtensionAction extends Action`, `ExtensionDataItem extends DataItem`, `Declaration` (validates args arrays, id rules, converts field / type arrays to core `Field` / `Type`), `Fire` (the `yaymatik_fire` handler: payload → refs / subject / facts → `Dispatcher::collect()`), `RunAdapter` (`Run` over a Scope), `Diagnostics` (option + Logger), `StepIndex` (missing-plugin index), `Guard` (one `call( module, callback, fn, fallback )` try/catch helper used by every call site in §9).
- **Registry**: `ModuleRegistry::modules()` fires `yaymatik_register` once, before building, with a `Registrar`; extension modules join the class-based ones. Today modules, steps and data items are class names built with `new $class()` (ModuleRegistry.php:55, :90, :146); `from()` / `collect()` / `data()` also accept instances, since an extension module holds its adapters as objects.
- **Two vocabularies, one public**: public type names (`string`, `number`, `money`, `boolean`, `date`, `enum`, `list` + `of`, `entity` + `item`) map to the internal `Core\Data\Type` and to the condition type (`DataItem::TYPE_*`): number/money → number, string, boolean, date, enum, list → list, entity → relation (not conditional).
- **No DB change.** Two options: `yaymatik_extension_errors` (diagnostics) and `yaymatik_extension_steps` (step index). No `DB_VERSION` bump. `Uninstaller` already removes `yaymatik_%` options on full removal.

### Runtime rules kept

- Loop guard: `Dispatcher::in_chain()` (Dispatcher.php:153–156, :320–332) already stops a workflow restarting itself through a run's own events, because `collect()` records the current run as parent (Dispatcher.php:109). `Fire` calls `collect()`, so a `yaymatik_fire` from inside a run is guarded the same way. That needs no `emits`. `emits` keeps its 1.0 meaning: the `may_refire` warning (Validator.php:224–242). CP2 proves both with a test.
- No core dedupe; `facts` stay narrow (§5.3): scalar types, ≤ 10 keys, ≤ 1 KB each, emails only as personal data. Runtime already reads plain trigger values (Scope.php:201–202); CP3 teaches the Validator, catalog, `Run::get()` and run detail.
- `Fire` returns at once when no active workflow uses the trigger (`Workflows::active_trigger_ids()`, the same cache `listen_active()` reads).

## Decisions

- **D1** No public class wraps an internal one and there is no `class_alias` (Q10): the public side is arrays, two hooks and the `Run` / `CustomerView` / `CartView` interfaces (D16). Adapters live in `Workflow\Extension\`, marked `@internal`.
- **D2** `Module` handle: `ok()` false → every method returns false and does nothing. Reasons recorded in Diagnostics: bad or reserved id, `requires_api` not met, duplicate module id, called after `yaymatik_register` ran.
- **D3** Declaration errors refuse that one declaration (diagnostic + `_doing_it_wrong()` under `WP_DEBUG`); the rest of the module loads. Unknown keys: ignored + `_doing_it_wrong()` under `WP_DEBUG`.
- **D4** Diagnostics: last 50 entries, one write per (module, callback) per 10 minutes (count++ in memory, flushed on the next write), also `Logger::error`. No auto-disable (Q12).
- **D5** Step index: refreshed when the registry is built and its fingerprint (md5 of the extension step ids + labels + outputs) changed. Entries are added and updated, never removed: a deactivated plugin's steps must stay known. One `update_option()` when it changed (autoloaded since CP4's review: the check runs on every request).
- **D6** Missing plugin (Q2): open / edit / save yes; a node whose step is unknown is kept only when the stored draft or live graph has the same node id with the same step (raw config, ≤ 64 KB); a new unknown node is still "Unknown step type.". Activate / Update blocked with `missing_plugin`. Already active: keeps running, the step is Skipped with "YayMail isn't active." A missing trigger fires nothing (`yaymatik_fire` finds no trigger; the plugin that would fire it is off anyway). Health check `missing_plugin`, no fix.
- **D7** Email capability: an internal interface `Core\Email\EmailStep` (`email_audience()`, `compose_email( config, Values, ?unsubscribe ): array`, `recipient( config, Values )`). `SendEmail`, `SendInternalEmail` and `ExtensionAction` with `email` implement it. `EmailPreview` and run detail read it, not step ids. Sending moves into `Core\Email\EmailDelivery` (recipient → unsubscribed → link → send → `to`), used by `SendEmail::run` and the adapter.
- **D8** Customer preview sample (Q4a): a trigger that provides `customer` but no `order` / `cart` previews with the newest customer account (`user:ID`); core Send email too.
- **D9** Templates: PHP chain → graph in `Workflow\Extension\TemplateBuilder` (positions from the same `ROW_GAP` as TS `flow.ts`, branch offset for `then` / `otherwise`). Shipped in meta (`automation.templates`), merged with the TS registry; the dev-only TS throw stays on core templates.
- **D10** Iframe editor: URL built by REST `POST /workflows/{id}/editor` (`{ nodeId, config }` → `{ url, sample }`); the app adds `yaymatik_embed=1&yaymatik_channel=<crypto.randomUUID()>`. The postMessage checks are exact (`origin`, `source`, `channel`, `version`).
- **D11** Run detail `result`: the catalog sends `result` (default the summary); `runResults.ts` fills `%output%` / `%field%` from the step's output and input for any step without a hand-written result. Email-capability actions default to "Sent to %to%".
- **D12** Ids: `^[a-z][a-z0-9_]{2,63}$`, prefixed with module id + `_`; reserved module ids from §5.1.
- **D13** (was O1, approved) CP9 example plugin is built from the acme reference: points trigger with `facts` + transient dedupe, add-points action, no-order email action with an iframe designer, template. It adds what acme lacks: data item `acme_rewards_reward` + `privacy_subjects` + `once_per` on a "Reward redeemed" trigger, and a `setup_issue`. No currency-switch trigger; CP0 changes contract §14 / §17 to say so.
- **D14** Real event for browser checks: the acme reference (`.claude/local/034-example-acme.php`, updated locally in CP0, not committed) and CP9's example hook `woocommerce_order_status_completed` and add `floor( order total )` points to the order's customer (accounts only) through `earn()`, which calls `do_action( 'yaymatik_fire', 'acme_rewards_points_earned', … )` behind Acme's hourly transient. Browser steps fire it by completing an order in WooCommerce › Orders and reloading admin pages (WP-Cron runs the jobs); no wp-cli in browser steps.
- **D15** Extension templates are checked only when the registry fingerprint changes (D5): `TemplateCheck` runs then, and the hidden ids + reasons are stored in the step index option. Admin page loads read the stored list; they never re-run the check.
- **D16** (Jack, Nov 13 11:47, `.claude/local/034-api-simplified.md`) Simplified public surface: fields and types are arrays / strings; triggers have no `listen` / `refs` / `subject`, they start with `do_action( 'yaymatik_fire', $trigger_id, $payload )`; payload keys `order_id` / `user_id` / `cart_id` / `review_id` / `<item>_id` become the run's data, the rest must be declared facts (unknown → dropped + diagnostic; missing `provides` → no run + diagnostic); subject = first of order → cart → review → user → module item; `customer` comes from the first of order → cart → review → user (a `user_id` beside an `order_id` doesn't change it); `Run::user()` = the order's account user, else the `user_id`'s user. `run( $config, Run $run )` returns `$run->done()` / `skip()` / `fail()`; anything else → Failed "The step returned no result." + diagnostic. `validate` returns `[ field => message ]`; `setup_issue` returns `''` when fine. `build( $config, Run $run )`. Any PHP callable everywhere. No `Result::wait`.
