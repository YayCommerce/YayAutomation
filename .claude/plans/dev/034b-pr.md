**Title:** feat: plan 034 PR B — Extension API v1: email actions, templates, iframe editor, example plugin

## Summary

Other plugins can now ship email actions, ready-made templates and their own designer inside YayMatik, on top of PR A's registrar (`docs/extension-api.md` §5.5–§5.6, §7).
- **Email actions:** an action with `email` gets Send email's Preview, Send test, unsubscribe link and headers, "Sent to …" and Skipped reasons. The plugin returns subject + HTML from `build( $config, $run )`; core renders merge tags, adds its unsubscribe footer when the HTML has no `$run->unsubscribe_url()`, and sends a full document as built (no WooCommerce styles inlined). Core email code reads a capability (`EmailStep`), not step ids.
- **Customer sample:** Preview of a trigger whose only data is the customer (e.g. Customer account created) uses the newest customer account, core Send email too ("Customer <name> data · nothing is sent").
- **Templates:** `$m->template( id, [ …, 'steps' => chain ] )`. Core builds and lays out the graph and checks it when the plugin's steps or templates change; a broken one is hidden with a diagnostic, one that needs setup is shown. Browse templates lists them in a group per plugin with its logo; "Before you start" adds the plugin's lines and "Set up <step> before you activate.".
- **Iframe editor:** an action with `editor` gets a button under its form that opens the plugin's own admin page in a full-screen modal; postMessage v1 with exact origin / window / channel / version checks; a `save` fills the step's field. The URL is built through REST and refused when it isn't on the admin's origin. `Api::references()` lists the values still used.
- **Example plugin:** `dev/example-extension/` ("Acme Rewards") uses every piece; `./run.sh check-extension` runs it end to end.
- **One placeholder syntax (D18):** every value YayMatik fills in catalog text is `{{ root.key }}`: `summary` `{{ config.<field> }}`, `result` `{{ output.<key> }}` / `{{ config.<field> }}`, a `required` message `{{ step }}`; `%s` only where a plugin calls `sprintf()` itself. Filled by the merge-tag parser (`fillTemplate()` / `Template::fill()`), no filters, a value never parsed again. A placeholder with another root or a filter writes a diagnostic (and `_doing_it_wrong()` under `WP_DEBUG`) and stays as written; the step is kept, since the check reads translated text. Core steps, the example and the .pot moved off `%x%` (no `php-format` on these strings); no back-compat (unreleased).
- **Fixes from PR A's browser checks:** Health check names the workflows that use an inactive plugin; a condition on a trigger fact in a run whose trigger plugin is off fails with a reason instead of a PHP notice.

Base: PR A's last commit (499fda2). **No schema change, no new option** (the step index option gains `checked` and `templates`). Contract: additive only (MINOR-compatible), every addition in §16's 1.0.0 entry.

**Setup after pulling:** run `pnpm wp-env start` — `.wp-env.json` (and `dev/wp-env-min/.wp-env.json`) map `dev/example-extension` to `wp-content/plugins/acme-rewards`.

### 0 Understand
The "Acme Rewards" example plugin now adds an email action designed in its own editor, a template, and a "Reward redeemed" trigger. Its email gets Send email's Preview, Send test and unsubscribe handling; its template shows in the library grid with its plugin icon; its designer opens over the workflow editor. - Deactivate older test workflows (PR A's checks and earlier runs), so only this run's workflows react.
- No Acme design yet: the example plugin has no way to delete one, so the steps run in this order: E6c, E7a–E7c with no design; then, on E7c's draft, E8d, E8a, E8b (creates "Design 1"), E8c, E8e, E7d; then E6a, E6b, E9, E10a, E10b.
