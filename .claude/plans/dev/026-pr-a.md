**Title:** feat: plan 026 — M7 PR A: cart tracking, settings, retention, privacy, health check

## Summary

The backend of M7 (ROADMAP-dev M7.1–M7.5) and its store-front part (M7.8). Carts of logged-in customers and guests are tracked in a new `yaymatik_carts` table. Guest emails are captured at classic and block checkout. A signed restore link refills a cart and opens checkout. A daily job deletes old runs and carts. WordPress's personal data tools can export and erase what YayMatik stores. Settings have a store and a REST endpoint. A health check finds stuck runs and late jobs and offers a fix for each.

There is no UI yet. The Settings page and the health check panel come in PR B (M7.6, M7.7). Until then, use REST to turn tracking on.

About 41 files, +4.5k, one commit per checkpoint.

  - Creating an order links it at once. A paid status marks the row `ordered`, and with a total over 0 it also marks other active carts with the same email. When an `ordered` cart changes, a new cycle starts.

## Check these first

After pulling:
1. `composer dump-autoload`. The autoloader is classmap-authoritative, and this PR adds new classes.
2. Load any wp-admin page. `wp_options.yaymatik_db_version` should be `5`, and the `wp_yaymatik_carts` table should exist.
3. Turn on tracking and capture from the console on a wp-admin page:
   ```js
   await (await fetch('/wp-json/yaymatik/v1/settings', { method: 'PUT', headers: { 'X-WP-Nonce': yayMatikMeta.wp.restNonce, 'Content-Type': 'application/json' }, body: JSON.stringify({ cartTracking: true, captureGuestEmail: true }) })).json()
   ```
4. Run `./run.sh check-carts`. Every line should be PASS. It uses temporary rows, orders and products and removes them afterwards.

## REST endpoints (`yaymatik/v1`, `manage_options`)
- `GET /settings` returns the six settings in camelCase plus `unsubscribeDefault`.
- `PUT /settings` takes a partial body. It returns 400 with `data.errors[{ field, message }]` when a value is out of range, and then nothing is saved.
- `GET /health/checks` returns `{ checks: [ { id, status: ok|problem|info, count, runIds, fix } ], checkedAt }`. `jobs_late` also has `guide`. When a read hits the 500-row cap, the run checks add `capped: true`.
- `POST /health/fix { check }` accepts `runs_queued`, `runs_running` or `cleanup_job`. Any other id gets a 400 `rest_invalid_param`. The server runs the check again itself, so it never uses ids from the client. It returns `{ fixed, checks }`.
- The `/health` ping is unchanged.

## Store front
- **Capture.** Guest emails typed at checkout are saved to the session's cart. This works on classic checkout (shortcode) and on the Checkout block. Every email is captured, registered or not, and the classic endpoint gives the same response for every input. A logged-in customer's cart always uses the account email.
- **Restore link.** `/?yaymatik_cart=<id>&yaymatik_token=…` adds the saved items to the current cart and redirects to checkout. The response sends `no-cache` and `Referrer-Policy: no-referrer`. A guest with an empty checkout gets the email and first name prefilled. A logged-in user's cart is never prefilled.
- **Notices.** These come from `wc_add_notice`:
  - "This cart is no longer available." (shop)
  - "You already placed an order for these items." (shop)
  - "We added your saved items to your cart." (checkout)
  - "Some items are no longer available." (checkout)

  The Checkout block prints no session notices on its own, so `RestoreCart` prints them above the block. That covers Storefront with the Checkout block. A block theme's store-notices block prints them first, so nothing shows twice.
- **Tracking off.** No capture and no tracking. Restore links in emails that were already sent still merge and redirect, but nothing is bound or written.

## Privacy
- **Exporter**, paged 50 at a time:
  - carts (items, dates, email, first name)
  - the unsubscribe record
  - runs about the person, in any status: workflow name or "Deleted workflow", start date, status, and the address each email was sent to
- **Eraser:**
  - Cancels waiting runs about the person ("The customer's personal data was erased.").
  - Replaces the email with `[deleted]` in `runs.scope` / `error` and `run_steps.input` / `output` / `error`. Whole JSON values only; text columns use address boundaries, so `jimbob@x.test` is left alone. Rows, statuses and dates are kept.
  - Deletes the carts on the last page. It keeps them when a queued or running run is about the person and asks the admin to erase again in a few minutes.
  - Keeps the unsubscribe record and says so.
- **Policy text.** A YayMatik section in Settings → Privacy → Policy Guide. It covers what carts and guest emails are saved before an order, what they're used for, and that they're deleted after the retention days.

## Cleanup job
- `yaymatik_cleanup` runs daily in the `yaymatik` group. It is scheduled on `action_scheduler_init`, at most one check per hour (`yaymatik_cleanup_checked_at`).
- It deletes carts first, then runs. Queued, running and waiting runs are never deleted, and neither is a run whose chain still has one of those. Whatever is left after the ~20 s budget is deleted the next day.

## Known limits
- A spoofed `X-Forwarded-For` skips the per-IP capture limit and can drain the site-wide one for 15 minutes (decisions M7 Cost).
- Emails taken from pending orders (D7 order created) are not rate limited.
- The capture counters are not atomic: a burst of parallel requests can pass a limit.
- A restored cart moves to the browser that first changes it; the browser it came from starts a new row without its email, unless it opens the link again.
- Restore is one click: a page on another site can make a browser open a valid link; the saved items go into that browser's cart, and an empty guest checkout gets the cart's email.
- Saved lines keep no cart item data, so products with add-on options come back without them.
- The health check reads at most the 500 oldest overdue runs (every running run, queued over 5 min, waiting past 15 min) and looks up jobs once or twice for each; a full read sets `capped: true` and `count` means "at least". Stuck runs newer than those 500 show only once older ones are fixed or finished. `POST /health/fix` reads twice (fix, then the checks it returns) and fixes the first 50 per call.
- `cleanup_job` reschedules a job that is over 1 h late; with WP-Cron broken it is late again later (`jobs_late` says why).
- Cleanup queries scan the runs and carts tables without an index; batches stop early because expired rows are the oldest ids. An index needs a schema change: after v1.0 if a store's tables are large.
